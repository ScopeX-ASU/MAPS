# MAPS v0.0.6 Refactor Architecture Inventory

This inventory records the current architecture before structural refactoring. It is intentionally descriptive: no ownership changes are proposed by this document.

## 1. Current top-level dataflow

The current inverse-design path can be summarized as:

```text
Device scaffold(s)
    |
    +--> LR device state
    +--> HR device state
    |
    v
BaseOptimization
    |
    +--> build parametrization / trainable parameters
    +--> generate transformed HR design/material state
    +--> convert HR design/material to LR resolution
    +--> fill LR/HR design regions
    +--> initialize sources / monitors / normalization
    +--> build ObjectiveFunc / SimulatedFoM
    +--> run backend simulation and objective evaluation
    +--> expose fields / epsilon gradients / parameter gradients
    +--> plotting / GDS / HDF5 export
    |
    v
InvDesign
    |
    +--> optimizer
    +--> schedulers
    +--> closure / backward
    +--> callbacks
    +--> plotting / checkpoints / diagnostics
    +--> optimization loop
```

The important observation is that the current code has a coherent scientific dataflow, but several different stages of that dataflow are implemented inside the same large classes.

## 2. `device_base.py`: responsibility clusters

`core/invdes/models/layers/device_base.py` is approximately 385 KB and is the largest architectural concentration point.

### A. Static device construction

The base device object owns fixed device-level state such as:

- simulation configuration;
- background material;
- geometry/port/structure configuration;
- device resolution and grid metadata;
- material maps;
- design-region definitions and masks;
- port configuration.

### B. Geometry and material rasterization

The same class contains logic for converting geometry/material configuration into maps used by the numerical backends, including geometry insertion and override structures.

### C. Grid and coordinate bookkeeping

The class owns native/export grid metadata, grid steps, coordinate conventions, slices, and conversions between native and auxiliary/export representations.

### D. Design-region bookkeeping

It creates and stores design-region masks and related metadata. This is a static physical scaffold; the actual trainable parametrization is currently created by `BaseOptimization` through `parametrization_builder`.

### E. Ports, monitors, and sources

The class owns a large family of methods for:

- creating port/monitor slices;
- generating mode and Gaussian source profiles;
- creating FDTD-X field monitors;
- storing source/monitor profiles;
- mode normalization.

The FDTD-X source/monitor path is directly implemented here rather than isolated behind a backend adapter.

### F. Simulation/backend construction

The device layer directly participates in constructing Ceviche/FDFD and FDTD-X simulations. This makes solver-specific execution details visible from the device abstraction.

### G. Field/objective support

Device-owned metadata is passed into objective construction, including ports, slices, native grids, cell weights, and epsilon maps.

### H. Thermal/electrical state

Thermal property maps, temperature-related material state, and current-control support are also attached to the same device abstraction.

### I. Plotting/export support

Field visualization and related debug/export support reach deeply into device-owned state. The plot path depends on device monitor slices, export-grid metadata, epsilon maps, and field solutions.

### Architectural conclusion

`DeviceBase` is simultaneously a physical-device model, geometry compiler, grid manager, port/source/monitor manager, backend preparation object, thermal state holder, and visualization data provider. This is the main source of its size and coupling.

## 3. `base_optimization.py`: responsibility clusters

`core/invdes/models/base_optimization.py` is approximately 124 KB.

### A. Configuration

Defines default simulation/optimization configuration and objective-fusion behavior.

### B. Parametrization construction

`build_parameters()` invokes `parametrization_builder(...)` and stores the resulting `nn.ModuleDict` as `design_region_param_dict`.

This is the current owner of trainable design-region modules.

### C. HR/LR material state

The constructor creates separate Torch epsilon tensors from `device.epsilon_map` and `hr_device.epsilon_map`.

The class then contains material-map realization logic, including region insertion, coverage-weight handling, shape fitting, coordinate extraction, resampling, and property-map resizing.

This is the current center of the HR-design → LR-design/material pipeline.

### D. Simulation initialization

Initialization directly calls `device.init_monitors()` and `device.norm_run()`, then builds the objective using extensive device-owned simulation metadata.

### E. Objective/simulation graph construction

`build_objective()` constructs backend-specific simulation objects and an `ObjectiveFunc`. For FDTD-X it directly invokes the device's FDTD-X simulation creation path.

### F. Gradient/forward dispatch

`cal_obj_grad()` and related methods bridge Torch/autograd, Ceviche, and FDTD-X paths.

### G. Thermal runtime state

The class snapshots, resolves, and plots runtime thermal state and thermal material maps.

### H. Visualization/debugging

`plot()` directly reads ObjectiveFunc solutions and device monitor/export metadata. It also resolves epsilon and epsilon-gradient maps and delegates to plotting utilities.

### I. GDS/HDF5/export

The class contains extensive high-resolution export logic, including upsampling, design-region extraction, GDS construction, port metadata, and HDF5 data dumping.

### Architectural conclusion

`BaseOptimization` is currently much more than an optimization model. It combines the differentiable parametrized-device state, HR/LR material compiler, simulation setup, objective construction, gradient bridge, thermal runtime state, visualization, and fabrication/export path.

## 4. `invdesign.py`: responsibility clusters

`core/invdes/invdesign.py` is the training/orchestration layer, but it still owns many unrelated concerns.

### A. Training configuration

Optimizer, learning-rate scheduler, sharpness scheduler, plotting, debugging, checkpointing, callbacks, and run configuration are all represented in one global configuration object.

### B. Optimizer/scheduler construction

`__init__` creates the optimizer and two scheduler instances from the device-optimization parameters.

### C. Nested optimizer closure

A nested `Closure` class is declared inside `InvDesign.__init__`. It owns zeroing gradients, forward evaluation, optional backward, optional gradient normalization, and result retention.

### D. Per-step orchestration

`before_step()`, `run_step()`, and `after_step()` control the optimizer lifecycle and callback execution.

### E. Debug/plotting

`after_step()` also constructs plotting requests and invokes `devOptimization.plot(...)`, including field, epsilon-gradient, and parameter-gradient visualization.

### F. CUDA diagnostics / memory lifecycle

CUDA memory accounting, garbage collection, result cleanup, and optional cache clearing are handled here.

### G. Checkpointing / export

The training loop also owns checkpoint and export behavior.

### Architectural conclusion

`InvDesign` is conceptually the closest class to the intended "training loop" abstraction, but it currently also contains substantial diagnostics, plotting, persistence, and closure implementation details.

## 5. Existing parametrization subsystem

`core/invdes/models/layers/parametrization/` is already a useful architectural boundary and should be preserved/strengthened rather than replaced.

Important current responsibilities include:

- parameter ownership;
- level-set/density/other parameterization implementations;
- symmetry transforms;
- interpolation and resolution conversion;
- subpixel/permittivity-space downsampling;
- lithography-related transforms;
- extrusion.

The current `base_parametrization.py` is itself broad, so it should eventually be decomposed, but only after the HR→LR materialization contract is isolated and tested.

## 6. Existing objective subsystem

The current architecture already separates some objective concerns into `ObjectiveFunc` and `SimulatedFoM`. This is a useful boundary.

However, the objective subsystem currently receives a large amount of device/backend-specific state directly from `BaseOptimization`, so the separation is incomplete.

## 7. Proposed ownership boundaries for the refactor

The inventory suggests the following target ownership without requiring an immediate rewrite:

```text
Device
    fixed physical scaffold
    geometry / material definitions
    ports / static design-region topology

DesignRegion / Parametrization
    trainable Torch parameters
    HR pattern construction
    HR transforms

Materialization / Resolution Pipeline
    HR pattern -> HR permittivity
    HR permittivity -> LR permittivity
    subpixel/permittivity-space conversion
    HR/LR region filling

Simulation
    physical evaluation definition
    sources / monitors / boundaries / grid

Backend
    FDTD-X / FDFD execution and tensor conversion

Objective
    FoM and objective fusion

Optimization
    model + objective + optimizer state

InvDesign
    training loop / scheduler / callbacks / persistence
```

## 8. Migration order implied by the inventory

The safe migration order is:

1. Preserve the current numerical/debugging behavior with the Phase 0 trace.
2. Extract the HR parametrization → HR permittivity → LR permittivity pipeline.
3. Extract static Device responsibilities from `BaseOptimization`/`DeviceBase` without changing semantics.
4. Isolate simulation specification from backend execution.
5. Isolate FDTD-X/FDFD adapters.
6. Shrink `BaseOptimization` into the differentiable model + objective composition.
7. Shrink `InvDesign` into the training loop.
8. Only after those boundaries are stable, remove duplicate/defensive/legacy code.

## 9. Refactor risk hotspots

The highest-risk transformations are:

- changing the HR→LR order or representation;
- changing subpixel/permittivity-space downsampling;
- changing when `device`/`hr_device` are populated with design-region material;
- changing gradient attachment to epsilon or level-set parameters;
- changing ObjectiveFunc construction or cached simulation state;
- changing field/gradient lifetime before plotting;
- changing GDS export source state.

These must be treated as explicit regression boundaries.
