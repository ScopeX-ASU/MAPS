# MAPS v0.0.6 Refactor Baseline

This document defines the immutable behavioral baseline for the `v0.0.6_refactor` development line.

## Protected baseline

- Reference branch: `release/v0.0.5_fdtdx`
- Refactor branch: `v0.0.6_refactor`
- Refactoring must not modify `release/v0.0.5_fdtdx`.
- Refactoring PRs must preserve scientific behavior unless a separate change explicitly changes behavior.

## Canonical 3D bending debug workflow

The primary interactive debugging workload is `core/invdes/examples/bending_3d.py`.

The baseline configuration uses:

- FDTD-X solver.
- 3D Bending device.
- 50 px/um simulation resolution.
- `subpixel=True`.
- Level-set design-region parametrization.
- HR device created from the LR device scaffold.
- HR design transforms followed by LR resolution conversion.
- 20 optimization iterations.
- Plotting enabled every iteration.
- Objective history, field plots, epsilon-gradient plots, and parameter-gradient plots are part of the practical debugging contract.
- GDS export is enabled for the debug run.

The refactor must preserve the ability to run this workflow for several iterations and inspect the same classes of diagnostics without requiring a different debugging path.

## Captured differentiable trace

A reference HDF5 trace is generated locally from the exact v0.0.5 FDTD-X bending workflow. The trace capture utility stores the native tensors needed for refactor equivalence checks:

- objective/breakdown values;
- simulated complex field arrays;
- LR epsilon;
- HR epsilon;
- LR epsilon gradients;
- HR epsilon gradients;
- design-region parameter gradients, including level-set knot gradients.

Use the trace comparison utility to compare a refactored run against the stored baseline. The HDF5 reference itself is intentionally kept outside the repository because it is a large machine-generated CUDA artifact.

## Existing validated numerical anchors

### MAPS 3D Bending

Previously CUDA-validated twice on the release baseline:

- forward modal power: approximately `1.208205413e-05`
- backward modal power: approximately `1.181784057e-07`

### MAPS 3D StraightWaveguide

CUDA-validated normalization/forward run:

- forward modal power: `0.991990447`
- backward modal power: `4.255047315e-06`
- normalization power: `1.0`
- frozen forward-power regression tolerance: `5e-3`

## Required behavioral dimensions during refactoring

The following must remain observable and comparable against the protected baseline:

1. Device construction and design-region topology.
2. Shared parametrization state.
3. HR design/material realization.
4. HR-to-LR resolution conversion, including subpixel/permittivity-space downsampling.
5. LR simulation material state.
6. Forward objective value.
7. Backward/gradient propagation to design parameters.
8. Field and gradient visualization/debugging workflow.
9. GDS/export path for the HR representation.
10. Numerical regression values where golden baselines already exist.
11. Full captured field/epsilon/gradient trace where the trace applies.

## Refactoring rule

A structural refactor is considered behavior-preserving only when the affected workflow continues to satisfy the applicable baseline tests and, for interactive/debug workflows, remains inspectable through the same key intermediate states and diagnostics.
